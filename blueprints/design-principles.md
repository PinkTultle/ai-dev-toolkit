# 설계 우선 원칙

> 도구 무관 공유 지식 — 모든 AI 코딩 어시스턴트에 적용

---

## 1. 설계 우선 원칙

**작업 크기에 맞는 절차를 밟는다.** 오타 수정이나 설정 변경처럼 요청만으로 할 일이 분명한
작업은 바로 구현하고 검증한다. 기능 추가·리팩토링·구조 변경처럼 결정할 것이 남아 있는 작업은
먼저 요구사항을 구체화하고 설계를 글로 남긴 뒤 구현한다.

- **설계는 사용자 승인 후 구현한다** — 설계 문서를 사용자가 확인하기 전에는 코드를 쓰지 않는다
- 더 나은 방법이 있으면 설계 단계에서 **능동적으로 대안을 제안**한다
- 구현을 마치면 설계 대비 결과를 확인하고, 확인한 근거와 함께 완료를 보고한다

### 절차를 수행하는 도구

이 라이브러리는 **개발 절차 자체를 정의하지 않는다.** 절차는 그 일을 전담하는 도구에 맡긴다.

| 환경 | 절차 수행 |
|------|----------|
| Claude Code + `superpowers` 플러그인 | superpowers의 구체화 → 설계 → 계획 → 구현 → 검토 흐름을 따른다 |
| Claude Code (superpowers 없음) | 기본 plan mode로 계획을 세우고 승인받은 뒤 구현한다 |
| 그 외 도구 | 해당 도구의 계획/승인 기능을 쓴다. 없으면 위 원칙을 대화로 지킨다 |

**설계 문서 위치는 절차 도구가 정한 곳을 따른다** (superpowers를 쓰면 `docs/superpowers/specs/`,
계획은 `docs/superpowers/plans/`). 이 라이브러리가 별도 위치를 강제하지 않는다.

설계와 구현의 일치도를 수치로 확인하고 싶을 때는 `gap-detector` 에이전트에 설계 문서 경로를 넘긴다.

## 2. 문서 디렉토리

절차 산출물과 별개로, 프로젝트에 누적되는 문서는 다음 두 곳에 둔다.

### 2.1 스택 지침 (`docs/stack/`)

프로젝트에서 발견한 패턴·컨벤션을 기술 스택별로 누적하는 디렉토리다.
- 파일명: `<언어 또는 프레임워크>.md` (예: `rust.md`, `react.md`)
- 사용자와 합의된 내용만 기록 — AI가 임의 추가하지 않는다

### 2.2 코드 설명 문서 (`docs/source/`)

소스 코드 트리를 미러링하여 코드별 설명 문서를 관리하는 디렉토리다.

```
docs/source/          ← 소스 트리와 동일한 구조
├── src/
│   ├── app/
│   │   └── main.md           ← src/app/main.c 설명
│   └── drivers/
│       └── uart.md           ← src/drivers/uart.c 설명
└── lib/
    └── protocol.md           ← lib/protocol.c 설명
```

**규칙:**
- 코드 파일(또는 모듈)을 구현·수정할 때 대응하는 문서를 `docs/source/` 아래 동일 경로에 생성/갱신한다
- 파일명: 소스 파일명에서 확장자를 `.md`로 변경 (예: `uart.c` → `uart.md`)
- 디렉토리 단위로 묶는 게 자연스러우면 디렉토리명 `.md`도 허용 (예: `drivers.md`)
- 내용: 모듈 목적, 주요 함수/클래스 역할, 의존 관계, 주의사항
- 코드 주석과 중복하지 않는다 — 주석은 "왜(why)", 문서는 "전체 그림(what/how)"

## 3. 기술 부채 명시

임시 방편이나 개선이 필요한 코드에는 반드시 표시:
```c
// TODO(이유): 설명 — 추후 [더 나은 방법]으로 개선 필요
// FIXME(긴급도): 설명 — 현재 [문제점] 발생 가능
// HACK: 설명 — [조건]에서만 동작하는 임시 코드
```
